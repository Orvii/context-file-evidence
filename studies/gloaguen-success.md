# Gloaguen et al. — does an AGENTS.md make an agent solve more tasks?

> **Primary source:** Thibaud Gloaguen, Niels Mündler-Sasahara, Mark Niklas Müller, Veselin Raychev, Martin Vechev. "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?" arXiv:2602.11988. ETH Zurich + LogicStar.ai. Full extraction: [research/evaluating-agents-md.md](../research/evaluating-agents-md.md).
>
> **Axis:** task success + cost + effort. **Study type:** experimental. **Agents:** Claude Code (Sonnet-4.5), Codex (GPT-5.2 and GPT-5.1 mini), Qwen Code (Qwen3-30b-coder) — four agent/model pairs.

## ⚠️ Read this before citing a number

**This paper has three versions and the headline numbers changed.** Almost all secondary coverage — including the widely-linked InfoQ piece (Mar 2026) — quotes **v1** (12 Feb 2026). The current arXiv version is **v3** (29 Sep 2026). The benchmark was even renamed between them.

| Benchmark name | **AGENTbench** | **CTXbench** |
| Developer-file gain vs none | "+4% on average" | "2.4% on average (p=21%)" |

This page uses **v3** as authoritative and flags every v1 number it also reports. Two phrases that circulate in blog posts do **not** appear in any version: the all-caps "**CTXBENCH**" spelling, and "agents follow instructions **almost to a fault**". The paper says "instructions in context files are well followed" and "agents generally follow instructions" — quote those, not the paraphrase.

## What it measured

Four coding agents on two benchmarks under three conditions — **None** (no context file), **LLM** (a context file generated by that agent's own recommended init command), **Dev** (the repository's real developer-written file):

- **SWE-bench Lite** — 300 tasks from popular Python repos, none of which ship a context file, so only None vs LLM applies.
- **The paper's own benchmark** (AGENTbench in v1, CTXbench in v3) — 138 instances drawn from 5,694 PRs across 12 Python repos that *do* have a committed root context file, built by a five-stage pipeline (find repos → filter PRs → set up environments → generate task descriptions → generate unit tests). All three conditions apply here.

One completion sampled per task per agent — no repeated runs.

## The headline result

**Context files did not improve task success, and cost more.** v3 abstract: *"providing context files does not generally improve task success rates, while increasing inference cost by over 20% on average."* The mechanism the authors identify: agents obey the instructions, the instructions add requirements and exploration, and *"unnecessary requirements from context files make tasks harder."*

The nuance that matters, and that the flat "context files hurt" headlines miss:

- **LLM-generated files are the problem, not files.** v3: developer files beat LLM files "by a significant margin of 7% on average" (CTXbench LLM-vs-Dev, Cochran-Mantel-Haenszel **p=0.038**). Developer files vs none is *not* significant (**p=0.21**) — a 2.4% point estimate with a p-value that cannot reject "no effect."
- **The v1 framing was stronger than the data.** v1 said developer files gave "+4%"; v3 walked that back to "2.4% (p=21%)" — i.e. not statistically distinguishable from zero. This is exactly why the version pin exists.

### Reasoning tokens

v3, verbatim: *"LLM-generated context files increase the average number of reasoning tokens by 22% for GPT-5.2 and 10% for GPT-5.1 mini on SWE-bench (respectively 14% and 10% on CTXbench), and developer-provided context files increase it by 20% for GPT-5.2 and 2% for GPT-5.1 mini."* (v1 said 14% for GPT-5.1 mini on SWE-bench, not 10%.) The authors read this as the file making the task *harder*: adaptive-reasoning models spend more thinking when handed more instructions to satisfy.

## The ablations — where the real finding is

v3 added ablations that v1 lacked, and they sharpen the conclusion from "files hurt" to something more useful:

- **Category ablation (Table 7):** removing the *testing*, *overview*, or *tooling* sections from an LLM-generated file never significantly improves accuracy, but removing *testing* significantly cuts cost (CTXbench p=0.023, SWE-bench p=0.0035). The sections make it expensive, not wrong.
- **Repository overviews are dead weight.** §4.3: *"context files ... are not effective at providing a repository overview"* — 95–100% of LLM-generated files include one, yet agents found relevant files no faster with it. This is the single most actionable finding in the paper: the part everyone writes first is the part that does nothing.
- **Stronger models don't generate better files (§4.4):** files generated by GPT-5.2+Codex beat each agent's own files by 2% on SWE-bench but *lose* 3% on CTXbench. The heading is literally "Stronger models don't generate better context files."

## What this study does NOT say

- It is **Python-only**, and the authors flag this as a threat to validity: Python is so well represented in training data that models may already "know" the repo's tooling, "nullifying the effect of context files."
- It does **not** measure wall-clock efficiency — that is [Lulla](lulla-efficiency.md)'s axis. This paper measures success, cost (USD) and steps.
- It does not test whether a *minimal, hand-tuned* file helps — only generated files and real-world developer files. The documentation-removal ablation is the closest, and its number was recovered from the PDF: **2.7%**. When all other docs are stripped and the context file is the *only* documentation, "LLM-generated context files not only consistently improve performance by 2.7% on average, but also out[perform developer-provided ones]" (v3 Appendix B, Figure 12; v1 §4.3/Figure 5 — same number). Read that alongside §5's main result and the paper's position becomes precise: context files are redundant *when documentation already exists*, and valuable *when they are the only documentation*. The file's marginal value is inversely proportional to how well-documented the repo already is. (Figure 12 prints no per-agent values; 2.7% is the only number, and the HTML hides it inside MathML — which is why first-pass scraping missed it.)

## Why it is in this grid

This is the success-rate pole, and it is the study that most directly contradicts the "faster and cheaper" reading of Lulla. It also supplies the reconciliation: the two are measuring different axes, and this one shows the cost of the file landing on *steps and reasoning* while the benefit, when it exists, is narrow and specific.
